How this site works.

I built and run everything you see here: five sections, one program, one server. This page explains what that program does, the decisions behind it, and how I know it still works after a change.

What it is

The site is one program written in Rust. A visitor asks for a page, the program reads what it needs from a small database, fills in an HTML template and sends back a finished page. There is no separate app to install, no framework to keep up with, and nothing to compile before a change goes live.

That choice is the reason a page arrives fast on a phone on mobile data, and the reason one person can maintain the whole thing. Everything below follows from it.

For a technical reader

Rust + Axum 0.8, SQLite through sqlx, Askama templates, HTMX with hx-boost for navigation, S3-compatible object storage for images, WebAuthn passkeys and PIN sign-in. One stylesheet. Twenty-four database migrations, run automatically at startup.

What happens when you open a page

Four steps, all on the same server. Nothing is fetched from someone else's service while the page is loading.

step 1 The front door nginx terminates the connection, limits request rates and serves cached files directly.
→ step 2 The program One Rust binary matches the address to a section and checks whether you are allowed to see it.
→ step 3 The data Text and numbers come from a SQLite file on the same machine; drawings come from object storage.
→ step 4 The page A template is filled in and sent as finished HTML — the browser has nothing left to assemble.

A worked example: uploading a drawing

Uploading used to take 39 seconds. It now takes about three. Nothing was removed — the slow work was moved out of the wait.

in browser The picture is shrunk to a web format before it leaves the phone, so the server never has to convert what the phone can. < 1 s
in request The file is stored, the row is written, and the finished card comes back. At this point I can close the tab. 2–3 s
after A smaller, slower-to-produce version of the image is made in the background and swapped in when it is ready. If it fails, the page still works. nobody waits

The rule I took from it: if a step does not change what the person sees next, it does not belong in the wait. The same rule shapes the rest of the site — images reserve their space before they load so the page never jumps, and the first image on a feed is given priority while the rest load as you scroll.

Who can see what

Sections like the food log hold personal data, so access is decided in one place and every page has to state which rule it uses.

visitor Sees the drawings, the practice board and the public pages. Nothing else exists as far as the site is concerned.
member Signs in with a name and PIN, and gets their own food log and their own sorting plans. A member cannot see anyone else's.
admin Manages drawings: uploads, captions, tags and whether something is listed. Being signed in is not enough on its own.
owner One account. Creates accounts, resets PINs, grants admin. An admin cannot do any of those, which means nothing granted can be turned back on the owner.
For a technical reader

Four session extractors, one per rule, so picking the wrong one is visible in the handler's signature. Admin routes answer a signed-in non-admin with a 404 rather than a 403 — a 403 would confirm the route exists. Every function that reads a post takes a required viewer argument, so forgetting it is a compile error rather than a leak. PIN attempts are counted in the database: five wrong ones lock the account for fifteen minutes, and a restart does not clear the count.

How I know it still works

A hobby project is where habits are cheap to build. These are the same ones I would bring to a team.

1105 + 458 Automated checks Tests covering sign-in, the database layer, the calorie maths and every game, plus 458 checks on the loading rules of the van board.
2 gates Fast check, full check A six-second check after every small piece of work, and one full run — formatting, linting, the whole test suite — before anything is called done.
tried in a browser Before it counts as finished A passing test proves the code runs, not that the screen is right. Anything a person touches gets opened and used first.
