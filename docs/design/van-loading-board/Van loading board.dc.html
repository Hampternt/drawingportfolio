Van loading board.

The screen a driver holds at the pallet while loading a delivery van, on the Hampter design system. Nine rows by two columns, loaded in reverse delivery order, with a side door that reaches only the first four rows.

Every figure, name and sentence on this page is produced by the rule set in docs/design/sorting-live/src/model.js — the same code the working prototype runs — so the design cannot drift from the logic it describes. Rebuild with node build.mjs.

S1

The board, mid-load

Route list only: nothing is known until it is tapped in. Olavstoppen is closed out and aboard, Jåtten is half in, and all three side spots are holding something — one green, two amber. The stack bar in each position is the whole point of this revision: its height answers “how full is the van” and its colour and code answer “who goes where”, so the two questions no longer need a view toggle between them.

S4

What every push button can say

Amber means allowed, and here is what it costs. Red means the van physically cannot, and only two situations are ever red. Every non-green state names the tap that clears it. These rows are rendered from real board states, not written out — the sentence beside each button is what the code emits.

Loading order agrees kind: ready
Push in → R1 · L

no explanation needed — this one is simply allowed

Someone else is up, and they are staged kind: order
Push in anyway

Olavstoppen goes in first — they are on SIDE 2.

Someone else is up, and they are aboard kind: order
Push in anyway

Tap Done on Olavstoppen first, or push this anyway.

Too tall for the window kind: split
Push in 4 of 12

All 12 will not stand at R2 · L — 5 is its ceiling. Split it 4 + 4 + 4: R2 · L, then R2 · R, then R3 · L.

Too thin for the window kind: thin
Push in anyway

Only 1 next to R1 · L’s 8 — 7 apart, and 5 is the floor here.

Side rows full, more than one crate kind: physical
Round the back

Rows 1–4 are full, so nothing more goes in this way — it would have to travel past what is already aboard. Carry this round to the back.

Side rows full, a single crate kind: doorway
Put it at the side door

One crate — the side door is the easy place to reach it from, and it keeps Jåtten Skole off anybody else’s stack. The freeze ware shares this space at the end.

S5

Where this differs from the previous draft

Seven things were wrong with the last board; these are the six this revision fixes and the one it does not.

✓ Two questions, one view

The space/identity toggle is gone. A taller stack bar carries fullness; the code beside it carries identity.

✓ Room for the map

Positions grew from 111×146 to 126px tall with a 26px bar, and the route strip shrank from 166px to 88px. The information is in better proportion to how often it is read.

✓ Warnings fold into what they are about

The capacity warning is now a state of the POSITIONS LEFT stat and the side-door budget lives on the door line, so neither is a band that appears and shoves the layout around.

✓ The doorways are drawn where they are

The back doorway is a column at the van’s rear across both bands; the side well sits at the end of the side-door row. Both are always visible, because both are real floor.

✓ Planned versus actual is structural

Dashed rungs above solid ones, not a tint.

✓ Identity is not colour alone

Every occupied position shows its three-letter code at all times, not only when the cell is too narrow for a name.

— A skipped tap still cannot be detected

Nothing here fixes that — the app has no independent view of the van. The route strip is labelled “as tapped in” to set the expectation, which is honesty rather than a solution.

S6

Notes on the design system

Two deliberate departures, both because this screen is used standing up in a cold warehouse rather than at a desk.

Controls are taller than the kit

The largest button in the system is --control-height-lg at 42px. The primary targets here are 48–60px, because the driver is often gloved and a dropped tap commits a crate to a position. Everything else — colour, type, radius, spacing — comes straight from the tokens.

No hover state carries meaning

This is a touch screen with no pointer. Anything the kit expresses through :hover has to also be visible at rest.
