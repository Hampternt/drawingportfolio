Commit `82e0053` (2026-07-04) guards `insert_drawing_task` against a stale
`image_id` and stops the S3 object being deleted on a failed transaction. It was
verified absent from `master` — `src/routes/tasks.rs` there called

returned the URL for S3 deletion without requiring the transaction to commit.

re-landed on master by a different path), so it was four commits of which **one
was worth rescuing and three were noise.**

**Rescued** onto `fix/stale-image-id` (off `master`, commit `53882c7`). The
cherry-pick conflicted on formatting only — master had `cargo fmt`-wrapped the
call across eight lines while the 2026-07 commit had it on one — resolved to
master's formatting with the branch's semantics. **This branch is unmerged and
unpushed; it needs a PR.**

> Why this hid so well: `git branch --merged` reports 9sazgl as unmerged, so it
> looks live, while three of its four commits are content-identical to work
> already on master. Ahead/behind counts cannot distinguish *superseded* from
> *pending* — only a file-level `git diff master...<branch>` can. Run that before
> deleting any branch that looks stale.
